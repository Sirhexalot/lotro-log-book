# 11. Risks and technical debt

The following points distinguish structural risks from confirmed defects. Priority and risk owner are not documented unless expressly stated.

- **Working tree and live version can diverge.** At the time of documentation, many files are changed or new and not committed. For a live finding, release manifest and published version must be considered as well.
- **Several build paths exist.** The PHP release and `baue_website.py` have different artefact shapes. A command from one flow does not automatically evidence the behaviour of the other.
- **Builds depend on data produced outside the repository.** `tools/build_php_data.py` reads `daten/*.json` and `web/*`; deed data additionally needs the external MagicQuestLog repository. Complete reproducibility is only possible with matching sources and versions.
- **Local source data is not fully in the repository.** Several generators read fixed configured paths in Companion/client/plugin installations. A checkout alone is therefore not necessarily enough for a complete rebuild; path, export state and external tool versions are release prerequisites.
- **Build order matters for the domain.** PHP page models consume already built quests, deeds, items, recipes, maps, vendor/faction/landmark data. An outdated predecessor can produce formally valid but domain-mixed indices; a single universal pipeline manifest with all source versions is not evidenced.
- **The data model is distributed and polyglot.** Relation generation lies partly in Python, partly in browser generators and partly in the PHP renderer. Short-key fields are not typed by a central JSON schema; regression tests and data space audits are therefore important contracts.
- **Real game semantics cannot always be derived from catalogue edges.** Map path, source, target, location and availability are different statements. Incomplete exports or unresolved identifiers must not be "repaired" via names or geometry without a dedicated rule with evidence.
- **External operational parameters remain relevant.** Rewrite rules, protection of the non-public release directories, PHP write permissions, Twig cache and actual runtime versions lie partly outside the application versioned in the repository.
- **Production rewrite rules lie outside the PHP release artefact.** The release builder copies no `.htaccess`; correct operation therefore also depends on the separately maintained web server configuration.
- **Documentation drift is already possible.** Existing documents contain dated or static build descriptions. Their statements only apply after alignment with current code and target environment.
- **Coverage and CI status are unknown.** Without measured coverage and verified CI configuration, no thresholds or "all checked" statements may be assumed.
- **Operational topology is only partly documented.** Provider, PHP/web server configuration, backups and monitoring are missing. Impact: incident resolution depends on implicit knowledge. Action: record operational owners and hosting configuration in a suitable operations document.
- **Filter contract and concrete UI occurrences are not everywhere in sync.** The open audit is in `docs/todos/entitaetenvertrag-abgleich.md`. Impact: inconsistent relation lists or row contents. Action: align contract, code and browser checks per entity together.
- **Map navigation mixes hierarchy levels.** 17 maps without a label produce, per language, 193 quest and 52 deed labels as well as 17 of 216 navigation names of the form `Karte <ID>`; six landscapes depict an area instead of a territory, and in Haradwaith six territories lie under one name. *Impact:* places are not findable, technical IDs look like game names. *Action:* naming from the areas in `parchmentMaps.xml`, merging the Helm's Deep variants, build check against `geoAreas.xml`; plan in [docs/archiv/kartenbenennung-hierarchie.md](../archiv/kartenbenennung-hierarchie.md).

These points are findings from the code/repository inspection, not a statement that the respective flows are currently faulty.
