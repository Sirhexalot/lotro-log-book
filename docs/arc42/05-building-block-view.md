# 5. Building block view

The entity and relation model with its diagram and its measured
quantities is kept in [docs/datenraum/entity-model.md](../datenraum/entity-model.md).

### 5.1 Data and build layer

- **Game and export data:** lie outside the normal PHP request and are processed by Python tools.
- **Web catalogues:** `build_daten.py` produces localised quest/deed files; further generators create items, recipes, travel, faction, landmark and instance data, among other things.
- **PHP data builder:** `tools/build_php_data.py` produces the localised inventory intended for PHP under `phpdata/`, including entity shards, page models, list models, indices and sitemap data.
- **Page models:** `tools/php_viewmodel.py` computes presentation data and links during the build so that PHP does not scan the whole catalogue for every page.

### 5.2 PHP application

| Building block | Responsibility |
|---|---|
| `php/public/index.php` | HTTP entry point, error status, API endpoint, legacy redirects, routing, sitemap output and dispatch |
| `php/public/router.php` | Development server router: serve existing files directly, otherwise hand over to the front controller |
| `Router` | Canonical paths, list/detail resolution, language paths, ID spelling, redirects and 404 |
| `Catalogue`, `Sprache` | Language codes, segment/URL tables, labels and selection for paths without a language |

| `Sets`, `Givers`, `Vendors`, `Landmarks`, `Factions`, `Titles`, `Instances`, `Adventures` | Domain-specific list/detail views; permitted filters and pagination for server-side browsers |
| `RelatedLists`, `FilterRegeln` | Resolving the detail page relations and the shared presentation threshold between direct list and filter |
| `Shell`, `View`, `Escape` | Shared HTML shell, Twig configuration, tracking/asset metadata and HTML escaping |

There are no persistent repository classes for a database server and no server-side authentication of the catalogue. Business logic is distributed across build view models, PHP list adapters, browser modules and templates; this division of responsibilities matters for changes.

### PHP data artefacts and read models

`tools/build_php_data.py` does not write a single monolithic catalogue. The central format consists of:

| Path/file group | Keying | Reader and purpose |
|---|---|---|
| `manifest.json` | build schema, languages, kinds and count per language | build/compatibility overview; no domain relation |
| `<sprache>/<art>/<shard>.json` | `entities[ID]`, bucket `md5(ID)[:2]` | `Data::entity()` for raw/list entities such as `q`, `d`, `i`, `recipe`, `set`, `giver`, `vendor`, `area`, `region` |
| `<sprache>/page-<art>/<shard>.json` | `entities[ID]` | `Data::page()` for Twig-ready detail models |
| `page-list/<shard>.json` | `pages[kanonischer Sprachpfad]` | `Data::listPage()` for type indices, sublists and pagination |
| `filter-q`, `filter-d`, `filter-i` | compact filter row by ID | `RelatedLists` and relational lists; no complete description text |
| `<sprache>/maps.json` | map table by map ID | map names and map paths |
| `*-index.json` | one compact row per entry or filter dimension | server-side browsers for quest givers, vendors, landmarks, factions, titles and instances |
| `<sprache>/sets-index.json`, `filter-items.json` | set/item facets | set and item lists |
| `<sprache>/deed-redirects.json` | old deed ID → current ID | canonical redirect of replaced duplicates |
| `<sprache>/zutaten-ohne.json` | item IDs without an evidenced source answer | disables empty source controls in recipe/crafting views |
| `<sprache>/abenteuer.json` | adventure blocks, areas, quests | adventure page; browser counterpart is additionally written under `web/` |
| `sitemaps.json` | sitemap index and canonical URL lists | `Sitemap::index()` and `Sitemap::section()` |
| `labels.json` | localised words, segments, families, icons and app metadata | `Catalogue`, `Shell` and templates |

The exact payload schema varies by kind and is determined by the writers in `tools/build_php_data.py` as well as by the readers `Data`, `RelatedLists` and domain classes. `manifest.json` does not document every field of a record and is not a JSON schema validator.

### 5.4 Data model: shape and identity

The data model is **not a relational database schema**. There are no SQL tables or foreign key checks at runtime. The authoritative records come from exports and generators; `tools/build_php_data.py` stores localised JSON entities, page models, indices and relation rows from them. PHP only reads these files. Relations are represented, depending on the case, as IDs in the source record, as ID lists resolved during the build, or as condensed display/filter values.

The builder knows the following catalogue kinds (internal identifiers): `q` quest, `d` deed, `i` item, `recipe` recipe, `p` profession, `title` title, `virtue` virtue, `set` set, `giver` quest giver, `vendor` vendor, `f` faction, `l` landmark, `area` area and `region` region. The complete generation can be traced in `language_data()`, `main()` and the view model functions of `tools/build_php_data.py` and `tools/php_viewmodel.py`.

IDs are usually held as strings and interpreted by their source type. Quest/deed/item IDs come from the catalogue data; map IDs come from the map table. Profession keys are stable keys. Area and region share the map data space but are stored in separate entity kinds according to `tier` (`map_kind()`). The shard is **not a domain key**: `md5(ID)[:2]` only determines which file a record is in. Language versions of the PHP data have the same domain IDs but localised names and output texts.

### 5.5 Entities and domain relationships

The table names the essential entities produced in the code and the evidenced relationships. "Direct" means that a source field or generator record explicitly carries the link. "Derived" means that the website build computes it from such statements. Such labels do not claim that the source relationship in the game has the same semantics as a website navigation.

| Entity / relationship | Source and key | Relationship in the website data model | Status and boundary |
|---|---|---|---|
| Quest (`q`) | `MQL_QUESTS`, identifier `i` | `pq` predecessor, `nq` next entry, `v` all prerequisites, `vo` alternative prerequisites, `e` excluding alternatives; `vl` level statement and `vb` additional prerequisite remain facts on the entry. | These fields are resolved in `build_relations()` only against existing quest IDs in the same quest inventory. Cross-references to deeds from the shared achievable space are therefore not automatically part of these quest page relations. |
| Deed (`d`) | `MQL_QUESTS` from the deed catalogue, identifier `i` | The same relation generation as for quests: predecessor, next entry, prerequisite, alternative, exclusion and back-reference to deeds that require it. Context list additionally by shared area or kind. | Sequence/prerequisite relations are source-field based; "same kind" and "same area" are derived context groups, not game prerequisites. Duplicate redirects are stored separately as old ID → current ID. |
| Quest ↔ quest giver (`q` ↔ `giver`) | `build_auftraggeber.py` creates `daten/auftraggeber.json`; `giver_viewmodel.py` joins its quest IDs with the quest inventory. | A quest giver has a list of assigned quests; quest detail can receive a quest giver link via `QUEST_GIVERS`. | The assignment follows the quest giver data source. Missing IDs, or IDs not present in the catalogue, are not emitted as a valid catalogue page when the linked views are generated. Multiple quest giver/location relationships are preserved in the index; the quest page link may use one selected quest giver. |
| Quest/deed ↔ item (`q,d` ↔ `i`) | `rw` (reward) in quest/deed sources; `quellen` in the item record. | Reward lists link items as far as an unambiguous ID exists; item pages group acquisition sources by quests or deeds. Name resolution via `item_link()` is linked only for exactly one match; ambiguous names remain unlinked. Map membership is derived and means "a source is maintained in this map path", not necessarily the find spot or target position of the item. |

**Shared record fields of quests and deeds:** `i` ID, `n` name, `g` quest giver name, `gt` quest giver location, `t` objectives, `s` steps, `rw` rewards, `v/vo/vl/vb` prerequisites, `rf` reputation source, `fk` map/navigation path, `x` session play and `e` excluding alternatives. `h` (enemy locations) and `hz` (locations of linked quests) are not interchangeable substitutes for a confirmed target position. The short keys are source format, not a globally typed schema. Evidence: `AGENTS.md` data sources as well as usage in `tools/php_viewmodel.py` and `tools/build_php_data.py`.

**Cardinality and direction:** `pq`, `v`, `vo`, `e`, rewards, map paths and source lists are multi-valued; `nq` is a single optional reference in the record. The build relation `required_by` is the inverse of `v` (not of `vo`). Recipe ↔ item is domain many-to-many and role-bearing (normal/optional ingredient, normal/critical result); quantities and roles belong to the edge. Set ↔ item and quest/deed ↔ area are likewise multiple assignments. The quest giver name `g` alone, by contrast, is a text fact and not a stable quest giver ID; `gt` is a location text/value and not synonymous with the map position. The PHP view models preserve these differences where the source supplies them.

### 5.6 Distinguishing stored relation, derived edge and presentation

The following distinction applies to interpretation:

1. **Source fact:** fields such as quest IDs in `pq`, `v`, `vo`, `e`; `fk` map paths; recipe ingredients/results; set members; landmark `targets`; faction `sources`. The website code receives or processes this source data. A source fact initially evidences exactly the stated assignment, not game rules beyond it.
2. **Build-derived relation:** `build_relations()` forms inverse quest prerequisites (`required_by`) and resolves IDs to names. `members_index()` derives area membership of items via their sources. Faction/title/landmark filter indices derive regions or hit counts from sources or targets. These values are reproducible derivations, not independent source records.
3. **Navigation or filter context:** quests/deeds with the same quest giver or rounded coordinate point as well as deeds of the same type or area appear as a connection. Shared `fk` path values control lists and filters. These groupings serve orientation; they are not a prerequisite, direct quest chain or unambiguous coordinate.
4. **Presentation link:** `php_viewmodel.py` and `RelatedLists.php` create clickable links from record IDs or already existing canonical URLs. A visible link is not always a standalone foreign key; it can be missing when an ID cannot be resolved or arise only in the view model when a name is unambiguous.

PHP does not hold the long relation lists completely in the page model: the view models often store only IDs such as `related_quests`, `related_deeds`, `related_used_in` and `related_crafted_by`. From these, `RelatedLists::forPage()` determines the shard types, loads only requested rows and fetches quest/deed/item hits from `filter-q`, `filter-d`, `filter-i` or recipe shards. Page list and detail models are thereby separate read models; JSON shards are a delivery format, not a canonical relational database.

### 5.7 Data model boundaries and key rules

If a base weapon or armour value is missing from the detail data and from the prepared item record, the PHP data build supplements the evidenced value from the complete export of **the same ID**. Damage types from this export require a client label. Attribute bonuses are not derived from base values or taken over from name variants.

- **No name keys as a substitute for IDs:** A name is display and search text. Item names become an item URL only when `ViewBuilder.item_link()` finds exactly one matching item.
- **A map name is display text, not an identity:** The name is derived from the language label, child prefix, English name or the assigned areas. Two maps may carry the same name; the map ID remains the key.
- **The navigation hierarchy is a projection:** `web/gebiete-<sprache>.js` groups quest labels and map IDs. It is neither the geography hierarchy from `geoAreas.xml` nor the map hierarchy from `parchmentMaps.xml`; region comes from `f[0]`, not from the map region code.
- **Area filters are a further projection of the same labels:** Quest and deed filters derive region/area from the respective catalogue data. A rename can merge area options and their counters but, without a change to `f[0]`, must change neither regions nor region totals. Quest and deed counters are checked separately from their filter indices.
- **No implicit completeness:** An edge that was not generated can mean that the source does not contain it, that the target is missing from the website catalogue, or that the builder in question does not output this relationship type. A missing link does not prove that the relationship does not exist in the game.
- **No character relations in the catalogue model:** Character progress from Companion is browser data and is not stored in `phpdata` as a catalogue foreign key.
- **Completed data instead of runtime join:** The PHP read format is separated by language and data type. The build phase can join several complete inventories; a single request reads individual record shards and prepared indices.
- **Indices are projections:** `givers-index.json`, `vendors-index.json`, `landmarks-index.json`, `factions-index.json`, `titles-index.json`, `instances-index.json` and page models contain subsets and aggregated values optimised for lists. They do not each replace the complete source record.

Evidence: `tools/build_php_data.py` (`build_relations`, `language_data`, the `members_index` call, shard/index writers), `tools/php_viewmodel.py`, `tools/related_filter_data.py`, `php/src/Data.php`, `php/src/RelatedLists.php`. The existing entity manifest `docs/datenraum/lotro-datenraum-entitaeten.json` is an alignment artefact for lists, filters and UI contracts; it does not on its own describe all source data or all edges.

### 5.8 Further data models of the browser applications

Not every website function is an entity edge in the PHP catalogue. The following data spaces are kept separately and must not be read into the core model:

| Data space | Identity and relationships | Boundary |
|---|---|---|
| Map metadata | Map ID, parent map, region code/tier, coordinate frame, image and assigned areas | Map ID and map position are not automatically a quest target or landmark; the map name is derived, not an identity |
| Map navigation (`web/gebiete-<sprache>.js`) | Labels from `f`, maps from `fk`, ID-based naming/display assignment via `referenz/gebietsansicht.json` | Display projection; names 17 unnamed maps after their assigned DAT areas and merges six Helm's Deep variants under one landscape; mixes territories, areas and map groups, is not a geography hierarchy |
| Region-and-area filter | Region/area and facet counters per quest or deed index | its own projection of the catalogue labels; area options can merge on renaming, region groups remain stable while `f[0]` is unchanged |
| Map start/compact/detail data | compact metadata for the first view; quest/deed IDs per area; full record on selection | UI loading levels of the same catalogue data, no additional domain entities |
| Travel | Stable master/travel nodes, directed or typed routes and travel skills in exported travel data | Route and travel skill do not prove that a particular character has unlocked the connection; no invented route line or travel time |
| Resource occurrences | Gathering type, area/map and resource occurrence point/count values | The point is a possible resource, not one specific item that certainly lies there |

#### Shared behaviour of the filter surface

- Shared browser filters read the state from URL parameters; if no explicit selection is present, the stored state `mql.filter.<bereich>.<sprache>` can apply. The URL wins over memory. Reset removes the area state. Relation filters write type-prefixed parameters (`q.*`, `d.*`, `recipe.*` etc.) so that tabs and parent path remain independent.
- Multi-checkboxes within one group are generally OR; different filter groups act as AND. Region/area trees permit only valid paths; a selected landscape restricts to that landscape within the region. The facets count candidates under the respective other current conditions, and active/counted options remain visible.
- Browser filters sort locally, filter before the page window and deduplicate by stable ID. Client lists use „Weitere anzeigen“ and sort optionally by name/level; PHP domain browsers deliver a GET form and numbered pages. These are two different pagination models, not one shared page limit.
- The shared filter surface replaces its GET fallback only after successful loading; on failure, „Als Seite öffnen“/fallback remains visible. Mobile filters are opened as a dialog; desktop shows the filter column next to the hits. Filter chips also show the non-removable default value of a single selection as a state chip.
- Progress filters and status colours exist only for entities with importable status and evidenced import basis. A missing status is not interpreted as completed, open, available or 0 %.

The reward browser uses the same item row as the item search. For each contract entity, list and detail address are stored in `tests/entitaeten_matrix.json`; the browser test `tests/browser_entitaeten_matrix.js` checks them.

### 5.10 Presentation grid, surfaces and row contract (status of 20.11.2026)

The surface is separated into three levels: shared tokens and grid in `web/gemeinsam.css`, components in `web/filter-ui.css`/`web/katalog.css`, page-related supplements in `web/{sets,gegenstaende,aufgabenfinder,entitaeten-listen,klassen,abenteuer}.css`.

**Grid and surfaces.** `--llb-raster` is a 12-column grid; `--llb-raster-abstand`, `--llb-flaechen-innen`, `--llb-flaechen-ton`, `--llb-flaechen-rand` and `--llb-flaechen-radius` form spacings and section surfaces. `.llb-raster` is the shared entry. Quest, deed and item details use a 7/5 grid for reading text and location preview; the location column fills its width without its own 320-px limit, the map image stays at 4:3 and at most the column width. If the location is missing, the column is omitted. Sections are surfaces with heading and inner spacing; „Woher“/„Wofür“ use the same full surface as a tab content even without tabs (`_detail_grid.twig`, `katalog.css`).

**Result rows.** Each list draws exactly one divider line per row; a container with its own border line and `.mql-row` with `border-top` must not overlap. `.mql-row` is a grid of hit, level and progress (two columns without progress, one without levels). Icon tile 64 px desktop/54 px mobile; icon flush left at the list edge. Column head labels have 8 px indent, the progress column ends flush right at the list edge. Level, progress and name start on the same top edge (`align-items:start`). Result names medium font weight, no permanent underline; additional info small. A column head is omitted when the list has no values for it. Designations stand in the head on desktop, at the value on mobile; several level types (recipes) keep their designation at the value.

**Filters.** `.filter-grid` uses the same 12-column grid: 3 columns filters, 9 columns results on desktop; below that single-column with a filter dialog. Range fields are real number fields with a dark colour scheme and light native spinners. Status filter at the top for quests/deeds: Alle, Nicht begonnen, Begonnen, Erledigt; additionally „Voraussetzungen erfüllt“ for quests with imported quest status. In the map list the filter button with count suffices; the selection opens below on desktop and as a dialog at the bottom on mobile. Progress is one field per entry, not additionally as a chip.

**Detail pages.** Title head (`_header.twig`) with type, 64/54-px icon and title; below it chips/progress, then sections. Quests and deeds: description, location (map), source/facts, rewards, objectives (collapsed), relations. Items: description/values, variants/set, then „Woher“ and „Wofür“ as tabs with two areas or as one surface with a heading. Short source lists remain a full surface; rewards use the same icon tiles as the lists. Relation lists keep the parent context and the 5/6 rule.

**Map detail column.** Head with type/title/54-px icon, labelled fact grid (level, quest giver, area, region, type, objectives, LOTRO points), exactly one progress field, then surfaces for description, „Was du tun sollst“, rewards, prerequisites, chain and „Wird vorausgesetzt von“. Links are recognisable as gold links with underline. Map points apply per step, not per objective; „Ziele auf der Karte ansehen“ shows the evidenced points. When the full data is loaded, the objects from the area shards are also supplemented so that description and steps do not remain empty.

**Overview navigation.** The overall map overview builds jump marks from the loaded area tree: regions, the Dunland group and „Weitere Inhalte“. East and West Rohan remain separate map groups under the one region mark Rohan, without their own jump marks. Under the group heads, maps are rendered with preview image and progress: Dunland with overview map and areas, East and West Rohan with their group maps. The maps use `kartenVorschau`/`gelaende.thumbnail` and load lazy like all others. This uses `MQL_GEBIETE`, `knotenFuerKarte` and the already loaded shards; no additional requests arise.

**Filter hierarchy.** The geography filter in the quest finder and map filter is built from the catalogue path `f` (region → area → sub-area) and thus corresponds to the map hierarchy. Four levels remain readable: 18 px indent per level, hanging indent for wrapped labels, a subtle guide line per branch and shortened group prefixes („Die Steppe“ instead of „Ost-Rohan: Die Steppe“). Paths carry `region`, `area` and optionally `teil` (cumulative sub-path). Selection on one level includes the sub-levels; facet counting uses the same `matches` rule. Example: Dunland-Überblick (505) → Dunland (361) → Galtrev/Tâl Methedras.
